# T-027 — Implement workspace authorization isolation for launch readiness

**Source finding:** AUDIT_REPORT.md §CTO-2 | Severity: P0 | Class: BROKEN / INSECURE  
**Assigned tier:** SENIOR  
**Effort estimate:** 4h | **Sequence:** independent

## WHAT
Enforces workspace data isolation for the Launch Readiness Planning module. Currently, `GET /api/launch/workspaces`, `DELETE /api/launch/workspaces/:id`, and evidence endpoints allow any anonymous client to list, mutate, or delete every other user's workspaces. This change adds an ownership token mechanism: creating a workspace generates a unique cryptographically secure access key (`workspace_token`), which is returned to the client and stored in `localStorage`. Subsequent reads and mutations (`GET`, `PATCH`, `DELETE` on workspaces, checks, and evidence) require this token via `X-Workspace-Token` header. `GET /api/launch/workspaces` only returns workspaces owned by the caller's token(s).

## WHY
Prevents unauthorized data destruction, eavesdropping, and cross-tenant regulatory evidence tampering on public deployments.
